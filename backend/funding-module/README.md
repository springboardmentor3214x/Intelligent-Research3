# Module 4 — Member 5: Funding Database, Search & FastAPI

This is a runnable scaffold covering everything in your role: model, search/filter,
pagination, saved funding, auth checks, and tests. It's built and verified —
all 12 tests pass and the server responds to real requests.

## Run it locally

```bash
pip install -r requirements.txt

# Populate sample data (safe to re-run — skips if data already exists)
python -m app.seed

# Start the server
uvicorn app.main:app --reload --port 8000
```

Then try:
```bash
curl http://localhost:8000/api/funding
curl -X POST http://localhost:8000/api/funding/search -H "Content-Type: application/json" -d '{"country":"USA"}'
```

Interactive API docs (auto-generated by FastAPI): http://localhost:8000/docs

## Run the tests

```bash
pytest -v
```

12 tests, covering: list/detail, keyword search, filters (alone + combined),
pagination correctness, unknown-ID 404, auth-required on save, no duplicate
saves, and users can't see each other's saved funding.

## Endpoints implemented

```
GET    /api/funding                    list + pagination
GET    /api/funding/{id}               details
POST   /api/funding/search             filtered search
POST   /api/funding/save               save (auth required)
GET    /api/funding/saved              list your saved funding (auth required)
DELETE /api/funding/saved/{funding_id} unsave (auth required)
```

## Before this goes anywhere near `main`

1. **Auth**: `app/auth.py` is a stub that trusts whatever's after "Bearer ".
   Swap it for Module 1's real JWT/session verification before this touches
   real user data — right now it has zero real security.
2. **Database**: Switch `DATABASE_URL` in `app/database.py` from SQLite to
   your team's Postgres connection string. Nothing else changes — SQLAlchemy
   handles the difference.
3. **Coordinate the schema with Member 4**: `research_areas`/`keywords` are
   stored as comma-separated strings here (SQLite-friendly, zero extra
   dependencies). In Postgres you'd likely use `ARRAY(String)` or a join
   table instead — agree on this together before Member 4 builds their
   ingestion pipeline against a schema you might change later.
4. **Migrations**: this uses `Base.metadata.create_all()` for simplicity.
   If the project uses Alembic elsewhere, generate a proper migration
   instead so schema changes are tracked.
5. **Status filtering**: search currently returns closed/expired opportunities
   too, unless filtered. Confirm with the team what the default behavior
   should be (e.g. hide closed by default, or let the frontend decide).
